# レビュー チェックリスト

Anthropic「Skill authoring best practices」に基づく、Skill レビューの詳細評価項目。
各項目は「合格基準」「よくある問題」で構成する。判定結果は
[report-template.md](report-template.md) の様式でレポート化する。

## Contents

- 1. Frontmatter 検証
- 2. 簡潔さ（Conciseness）
- 3. 指示の具体度（Degrees of freedom）
- 4. スキルの構造
- 5. 命名規約（Naming）
- 6. 用語の一貫性・時限情報
- 7. ワークフロー
- 8. 例示（Examples / Templates）
- 9. スクリプト品質（該当時のみ）

## 1. Frontmatter 検証

YAML フロントマターは Skill 発見の要であり、最優先で点検する。

**合格基準:**
- `name`: 最大64文字。**小文字・数字・ハイフンのみ**。XMLタグ不可。予約語
  `anthropic` / `claude` を含まない。ディレクトリ名と一致している。
- `description`: 非空。最大1024文字。**三人称**で記述。XMLタグ不可。
  「**何をするか**」と「**いつ使うか**（トリガー・文脈）」の両方を含む。
- `metadata.author`: **必須**。作成者を明記している。
- 任意フィールド（`user-invocable` 等）が使われている場合、値が妥当である。

**よくある問題:**
- description が一人称（"あなたは…使えます"）→ **Critical**。
  発見精度を下げる。三人称（"〜する"）に直す。
- description が "ドキュメントを作成" のように曖昧で、いつ使うかが不明 →
  **Warning** 相当。具体的なトリガー語・対象を追記する。
- `name` に大文字・アンダースコア・スペース、または予約語が含まれる →
  **Critical**（規約違反でロードに支障）。
- `metadata.author` の欠落 → **Critical**。
- name とディレクトリ名の不一致 → **Critical**。

良い description の例（三人称・何を/いつ）:
> Excel スプレッドシートを分析し、ピボットテーブルやグラフを生成する。Excel ファイル
> や .xlsx、表データを扱うとき、またはユーザーがスプレッドシート分析を依頼したときに
> 使用する。

## 2. 簡潔さ（Conciseness）

コンテキストウィンドウは共有資源。Claude が既に知っていることは書かない。

**合格基準:**
- 各説明が「Claude がこれを本当に必要とするか」を満たしている。
- 一般概念（PDFとは何か、ライブラリの使い方など）の冗長な前置きがない。
- トークンコストに見合う情報のみを含む。

**よくある問題:**
- 自明な概念説明が段落単位で存在する → **Suggestion**（削減を提案）。
- 同じ内容の言い換え・重複 → **Suggestion**。

## 3. 指示の具体度（Degrees of freedom）

タスクの壊れやすさ・変動性に応じて指示の具体度を合わせる。

**合格基準:**
- 複数の妥当なアプローチがある／文脈依存の判断 → 高自由度（テキスト指示）。
- 望ましいパターンがある／設定で挙動が変わる → 中自由度（擬似コード・引数付き
  スクリプト）。
- 壊れやすく・一貫性が重要・厳密な順序が必要 → 低自由度（固定スクリプト、
  「コマンドを変更しない」等の明記）。

**よくある問題:**
- 壊れやすい操作に曖昧な指示しかない → **Warning**（手順を固定化すべき）。
- 自由度の高い創造的タスクに過度な手順固定 → **Suggestion**（裁量を許す）。

## 4. スキルの構造

SKILL.md は目次的な概要に留め、詳細は必要時に読む別ファイルへ。

**合格基準:**
- **SKILL.md 本文が500行以内**。超える場合は別ファイルへ分割。
- 参照ファイルへのリンクが **SKILL.md から1階層のみ**（参照先がさらに別の
  参照を辿る入れ子構造になっていない）。
- 200行を超える参照ファイルには冒頭に目次がある。
- 複数ドメインを扱う場合、ドメイン別にファイル分割されている。
- ファイル名が内容を示す（`doc2.md` ではなく `form_validation_rules.md`）。

**よくある問題:**
- SKILL.md が500行超 → **Warning**（分割を提案）。
- 参照が2階層以上（SKILL.md → a.md → b.md）→ **Warning**。Claude が
  b.md を部分読みし情報欠落するおそれ。1階層に再構成する。
- 長い参照ファイルに目次がない → **Suggestion**。

## 5. 命名規約（Naming）

**合格基準:**
- スキルの意図が明確に伝わる名前であること (例: `processing-pdfs`, `analyzing-spreadsheets`) 。
- Skill 群の中で命名パターンが一貫している。

**よくある問題:**
- `helper` / `utils` / `tools` / `documents` / `data` など曖昧・汎用すぎる名 →
  **Warning**（具体的な活動名に）。
- 予約語を含む名（`claude-tools` 等）→ **Critical**（§1 と重複指摘可）。

## 6. 用語の一貫性・時限情報

**合格基準（一貫性）:**
- 1つの概念に1つの用語を使い続けている（例: 常に「APIエンドポイント」。
  「URL」「path」等と混在させない）。

**合格基準（時限情報）:**
- 「2025年8月まではこちら」のような将来陳腐化する記述がない。
- 古い情報は "旧パターン" 節に隔離されている。

**よくある問題:**
- 現在の日付により処理を分岐させる指示 → **Warning**（"旧パターン" 節へ退避するか削除）。

## 7. ワークフロー

**合格基準:**
- 複雑な操作が明確な逐次ステップに分解されている。
- 特に複雑な手順にはコピー可能なチェックリストがある。
- 品質が重要なタスクに「検証→修正→再検証」のフィードバックループがある。
- 分岐がある場合、判断ポイントが条件付きで明示されている。

**よくある問題:**
- 多段階処理が一括の散文で、ステップ分解されていない → **Suggestion**。
- 検証ステップがなく、誤りを早期に捕捉できない → **Suggestion〜Warning**。

## 8. 例示（Examples / Templates）

**合格基準:**
- 出力品質が例に依存するタスクで、入力／出力ペアの具体例が提供されている。
- 例が抽象的でなく具体的である。
- 出力様式が必要なタスクで、厳密さに応じたテンプレートが示されている。

**よくある問題:**
- 例が "適切に処理する" 等の抽象記述のみ → **Suggestion**（具体例を追加）。

## 9. スクリプト品質（該当時のみ）

Skill が実行スクリプトを含む場合のみ評価する。マークダウン指示のみの Skill では
このセクションをスキップする。

**合格基準:**
- エラー条件を Claude に丸投げせず、スクリプト内で明示的に処理している。
- 定数に根拠がある（voodoo constants 排除。`TIMEOUT = 47` のような不可解な値が
  ない／コメントで理由を説明）。
- ファイルパスがすべて **forward slash**（`scripts/helper.py`）。Windows 形式
  （`scripts\helper.py`）を使っていない。
- 必要パッケージが明記され、利用可能性が確認できる（インストール前提の暗黙依存が
  ない）。
- MCP ツール参照が完全修飾名（`ServerName:tool_name`）。
- 実行か参照かの意図が明示されている（例: "〇〇アルゴリズムを実行する" / "〇〇アルゴリズムを参照する"）。
- 破壊的・バッチ・高リスク操作に検証ステップ（plan-validate-execute）がある。

**よくある問題:**
- Windows 形式パス → **Warning**（Unix で動作しない）。
- 根拠不明の定数 → **Suggestion**。
- 例外を握りつぶさず Claude に投げて終わるスクリプト → **Warning**。
- 必要パッケージが明記されていない。またはインストールされていない場合の対処がない → **Warning**。
- MCP ツール参照が不完全 → **Suggestion**。
- スクリプトが破壊的操作を行うのに検証ステップがない → **Warning**（plan-validate-execute を追加することを提案）。
- コードコメントが全く無いか、すべて英語 → **Warning**（日本語でのコメントを推奨）。
