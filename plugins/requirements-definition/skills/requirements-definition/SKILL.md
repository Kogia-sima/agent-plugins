# 要件定義ヒアリングスキル

ユーザの漠然とした要望を入力として受け取り、**ヒアリングを通じて要件を具体化したうえで、実装可能なレベルのシステム要件定義書を出力する**スキル。出力は **Artifacts に Markdown 形式** で生成する。

このスキルの成果物は、**プロジェクトをよく知らない人が初めて読んでも、要件をすべて正しく理解して実装を進められる粒度**であることを最優先の品質基準とする。

## このスキルが解決する課題

開発の失敗の多くは、コードの品質ではなく **要件の曖昧さ** に起因する。ユーザは「こういうものを作りたい」というイメージは持っていても、それを実装者へ過不足なく伝える形に分解できていないことが多い。

一方で、何を確認すべきかはシステムの種類によって大きく変わる。同じ「管理ツールを作りたい」でも、Web アプリかバッチ処理かで、確認すべき非機能要件もデータ要件もまったく異なる。

そこでこのスキルでは、要件定義書を書き始める前に必ず **対話的なヒアリング** を行い、**すべての要件が具体的になるまで** `ask_user_input_v0` ツールで質問を繰り返す。曖昧なまま推測で埋めることはしない。

## ワークフロー全体像

このスキルは4つのフェーズで構成される。

1. **要望の受領と初期分析**: 実現したいことを把握し、システムの種類・不明点・実現性の懸念を洗い出す
2. **ヒアリング**: `ask_user_input_v0` ツールで、要件が具体化するまで繰り返し質問する
3. **要件定義書の作成**: 規定の構成に従い、Markdown 形式の Artifact として出力する
4. **フィードバック対応**: ユーザの指摘の妥当性を判断し、要件定義書に反映する

各フェーズの詳細は以下の通り。

---

## フェーズ1: 要望の受領と初期分析

ユーザが要望を提示してきたら、この段階ではまだ要件定義書を書き始めない。まず以下を整理する。

- **システムの種類**: Web アプリ / モバイルアプリ / API・バックエンド / バッチ・データ処理 / CLI ツール / デスクトップアプリ / 組込み のどれに近いか
- **目的と解決したい課題**: なぜこのシステムが必要なのか、現状の何を改善するのか
- **利用者と利用規模**: 誰が使うのか、想定ユーザ数・同時アクセス数の桁感
- **不明点**: 後述の「要件の具体性チェックリスト」のうち、要望から読み取れず、要件定義書の品質に影響する項目
- **実現性の懸念・代替案の有無**: 技術的・コスト的に困難な点や、より適した実現方法がないか

### 実現性の懸念がある場合の対応(必須)

ユーザの提示した要望が **技術的・コスト的に実現困難** な場合、あるいは **要望よりも適した実現方法がある** 場合は、要件定義書を書き始める前に必ず以下を行う。

1. 懸念点または、より良い案を **率直に、根拠とともに提示する**
2. **代替案を1〜3個提示する**(それぞれのトレードオフ: 実現性・コスト・期間・複雑さが伝わるように)
3. ユーザに選択してもらい、**合意を取ってから**先に進む

実現不可能な要望や、明らかに筋の悪い構成のまま要件定義書を作って渡してはならない。ただし押し付けず、最終判断はユーザに委ねる。

### ヒアリングが不要なケース

ユーザが最初のメッセージで「要件の具体性チェックリスト」の項目をすべて明示しており、実現性の懸念もない場合に限り、フェーズ2を省略してフェーズ3へ進んでよい。この場合でも、置いた前提があれば要件定義書を書く前に「**以下の前提で進めます**」と明記して確認する。

---

## フェーズ2: ヒアリング

初期分析で洗い出した不明点を、**`ask_user_input_v0` ツールを使って**質問する。文章で質問を羅列せず、必ずこのツールでタップ可能な選択肢として提示する。

### ヒアリングの設計原則

- **1回のツール呼び出しで最大3問まで**。それ以上は、要件への影響が大きい順に絞り込む
- 各質問の選択肢は **2〜4個で相互排他的** にする
- 会話の中で既に答えが分かっている項目、要望から確実に推測できる項目は質問しない
- 選択肢で表現しきれない自由記述が必要な項目(具体的な業務ルール、計算式など)は、選択肢に「その他(自由記述で補足)」を含めるか、ツールでの確認後に文章で深掘りする

### 「要件の具体性チェックリスト」

以下のすべての項目が **具体的になるまで** ヒアリングを繰り返す。1項目でも曖昧なまま要件定義書を書き始めてはならない。各項目の確認は1回のツール呼び出しに詰め込まず、関連する項目ごとに複数ターンに分けてよい。

| カテゴリ | 確認すべき内容 |
|---------|--------------|
| **目的・背景** | なぜ作るのか、解決したい課題、成功の定義 |
| **利用者** | 利用者の種類(ロール)、想定ユーザ数、利用環境(PC/モバイル/社内のみ等) |
| **主要機能** | システムが「できなければならないこと」。各機能の入力・処理・出力 |
| **データ** | 扱う主要なデータの種類、入出力フォーマット、想定データ量・件数の桁感 |
| **外部連携** | 連携する既存システム・外部 API・認証基盤の有無 |
| **非機能** | 性能(応答時間・スループット)、可用性、セキュリティ要件、対応ブラウザ/OS |
| **制約** | 技術スタックの指定、予算・期限、既存資産の流用、法令・社内規程 |
| **画面の有無** | ユーザが操作する画面が必要か(必要なら主要な画面の洗い出しへ) |

### ヒアリングの進め方の目安

1巡目で「目的・利用者・主要機能・画面の有無」など全体像を確定し、2巡目以降で「データ・非機能・外部連携・制約」を詰めていくと、質問が噛み合いやすい。全体像が見えないまま細部を聞くと、ユーザが答えにくい。

### 回答が得られない場合の対応

- 「**分からない**」「**お任せ**」と回答された項目: そのシステム種別で最も標準的と思われる前提を **明示し**、「この前提で進めます」と宣言してから進める。黙って勝手に決めない
- 非機能要件など、ユーザが判断材料を持たない項目: 一般的な水準(例: 想定ユーザ数からの妥当な同時接続数)を提案し、合意を取る

### ヒアリングの終了判定

「要件の具体性チェックリスト」の全項目が、**実装者がそれを読んで迷わず判断できる粒度**になったらヒアリングを終了する。終了前に、確定した要件の要約を簡潔に提示し、「**この内容で要件定義書を作成してよいか**」を確認する。

## フェーズ3: 要件定義書の作成

ヒアリング結果を踏まえ、システム要件定義書を **Markdown 形式の Artifact** として作成する。

### 全体ルール

- **作成者・改訂履歴・承認欄などのメタ情報は含めない**。要件の内容そのものだけを記載する
- 図(アーキテクチャ図、データフロー、画面遷移、状態遷移など)は **すべて Mermaid 記法のコードブロック** (` ```mermaid `) で記述する。画像や ASCII アートは使わない
- **実装者目線で具体的に書く**。「ユーザを管理する」ではなく「ユーザの登録・一覧表示・編集・論理削除ができる」のように、何ができれば完成かが判定できる粒度にする
- ヒアリングで確定しなかった事項を勝手に創作しない。やむを得ず前提を置く場合は、該当箇所に「**(要確認)**」と明記する

### 必ず以下の構成で出力する

```markdown
# [システム名] システム要件定義書

## 1. システム概要
### 1.1 背景
### 1.2 目的
### 1.3 システムの役割・スコープ
### 1.4 利用者・ステークホルダー
### 1.5 システム構成・アーキテクチャ
### 1.6 前提・制約

## 2. 機能要件

## 3. 非機能要件

## 4. データ要件

## 5. 画面一覧
```

### 各章に記載する内容

**1. システム概要**
- 背景・目的・解決する課題を、前提知識のない読者にも分かるように記述する
- システムの役割と **スコープ(対象範囲と対象外)** を明示する
- 利用者の種類(ロール)とそれぞれの関わり方を記述する
- アーキテクチャは **Mermaid のフロー図またはコンポーネント図** で示す(クライアント・サーバ・DB・外部連携などの構成要素と関係)
- 採用が確定している技術スタックや前提・制約を列挙する

**2. 機能要件**
- 主要機能ごとに、`FR-01` のような **一意の機能 ID** を付与する
- 各機能について「**概要 / 入力 / 処理内容 / 出力 / 事前条件・制約**」を記述し、実装者が振る舞いを再現できる粒度にする
- ロールごとに使える機能が異なる場合は、機能と権限の対応を明示する
- 複雑な業務フローや状態遷移がある場合は Mermaid のフロー図・状態遷移図を添える

**3. 非機能要件**
- 性能(応答時間・スループット・同時接続数)、可用性、拡張性、セキュリティ(認証・認可・データ保護)、運用・保守、対応環境(ブラウザ/OS)などを **可能な限り数値・具体条件** で記述する
- 「高速であること」のような測定不能な表現は避け、「主要画面の応答は通常時2秒以内」のように判定可能にする

**4. データ要件**
- システムが扱う主要なデータ(エンティティ)ごとに、項目名・型・必須/任意・桁数や制約を **表形式** で定義する
- 入出力データのフォーマット(JSON / CSV / 帳票など)とサンプル構造を示す
- 想定データ量・件数・増加見込みの規模感を記述する
- エンティティ間に関連がある場合は Mermaid の ER 図(`erDiagram`)で示す

**5. 画面一覧**
- 操作画面が必要なシステムの場合のみ記載する。不要な場合(API・バッチ・CLI など)は、この章に「**本システムは操作画面を持たない**」と一文記す
- 各画面について「**画面 ID / 画面名 / 目的 / 主な表示項目・操作 / 関連する機能要件 ID**」を表形式で記述する
- 画面間の遷移がある場合は Mermaid のフロー図で画面遷移図を示す

### 出力後の一言

要件定義書を提示したら、「**粒度や記載内容に過不足があれば調整します**」と添え、フェーズ4の対話の余地を残す。

## フェーズ4: フィードバック対応

提示した要件定義書に対してユーザからフィードバックがあった場合、**指摘をそのまま鵜呑みにせず、まず妥当性を判断する**。

### 判断と対応の手順

1. **妥当な指摘の場合**(記載漏れの指摘、より正確な情報の提供、合理的な仕様変更など): 要件定義書(Artifact)を更新して反映する。関連する他の章に波及する場合は、整合性が取れるよう併せて修正する
2. **妥当でない、または懸念がある指摘の場合**(他の要件と矛盾する、技術的に実現困難になる、スコープが過度に膨張する、セキュリティ上問題があるなど): **勝手に反映せず**、なぜ懸念があるかを根拠とともに説明し、ユーザに確認・再合意を取ってから対応を決める
3. **意図が不明確な指摘の場合**: 推測で反映せず、何を変えたいのかを確認する

要件定義書は対話を通じて育てるものとして扱い、「**他に追記・修正したい点があれば教えてください**」という姿勢を保つ。

---

## 重要な姿勢

### 「実装者が迷わないか」を判断軸に置く

粒度に迷ったら「**このプロジェクトを知らない実装者が、これを読んで実装に着手できるか**」に立ち返る。曖昧な表現が残っていれば、それはヒアリングが足りていないサインである。

### 推測で埋めない、勝手に決めない

不明な要件を推測で埋めると、後工程で手戻りが発生する。分からないことは聞く。やむを得ず前提を置くときは必ず明示し、ユーザの合意を取る。

### 要件の完全性より、確定の確実さを優先する

すべてを一度に詰めようとして質問攻めにすると、ユーザが疲弊する。全体像から詰めていき、各ターンで確実に1段階ずつ具体化する。

---

## 想定外の入力への対応

- **要望が大きすぎる/抽象的すぎる場合**(例: 「業務を全部効率化するシステム」): いきなり全体を要件化せず、まず対象業務やスコープを絞り込むヒアリングを行う。最初のリリースで実現する範囲を区切って扱う
- **複数のシステムが混ざっている場合**: 分けて確認し、今回の要件定義書で扱う対象をユーザに選んでもらう
- **既存の要件メモや仕様書がある場合**: ゼロから作り直さず、その内容を読み取って不足・曖昧な点をヒアリングで補い、規定の構成に再整理する
- **実現性に重大な懸念がある場合**: フェーズ1の手順に従い、要件定義書を書く前に懸念と代替案を提示して合意を取る
- **法令・コンプライアンス・専門領域が絡む場合**(個人情報、決済、医療など): 該当する非機能要件・制約として明示し、専門家・法務の確認が必要な旨を要件定義書に注記する
