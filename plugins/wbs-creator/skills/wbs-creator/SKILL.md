# WBS生成スキル

プロジェクトのゴールを入力として受け取り、**表形式のWBS（Work Breakdown Structure）** を出力するスキル。各タスクは「半日〜2日程度で完了できる粒度」まで分解し、担当者が迷わず着手できる状態にする。

## このスキルが解決する課題

「何をすればいいかは分かっているが、誰が・いつ・何を・どの順番でやるかが整理されていない」状態を解消する。WBSは単なるタスクリストではなく、**フェーズ構造・依存関係・成果物・工数**を一覧で把握できる計画の骨格である。

適切なWBSがない状態では以下の問題が起きやすい:

- タスクの抜け漏れが判明するのが後工程になる
- 並行作業と直列作業の区別がつかず、スケジュールが非効率になる
- 担当者がタスクの完了基準を自己判断できず、品質がばらつく

---

## ワークフロー全体像

このスキルは4つのフェーズで構成される:

1. **ゴールの受領と初期分析**: プロジェクトの性質・規模・前提を把握し、不明点を特定する
2. **コンテキストヒアリング**: `ask_user_input_v0` ツールで不足情報を確認する
3. **WBS設計**: フェーズ・タスク・依存関係・工数を設計する
4. **表形式での出力**: 規定のカラム構成でWBSを提示する

---

## フェーズ1: ゴールの受領と初期分析

ユーザからゴールを受け取ったら、まずタスクを書き始めずに以下を内部で整理する:

### 確認すべき項目

| 項目 | 分解への影響 |
|------|------------|
| **成果物の形式** | Webページ・ドキュメント・システム・イベントなど、何が「完成品」かによってタスク構成が変わる |
| **関係者・承認フロー** | 上長承認・レビュー・合意形成のステップが必要かどうか |
| **利用ツール・環境** | 既存のツール・プラットフォームがある場合、新規構築タスクを省略できる |
| **期限・リソース制約** | 期限がある場合は逆算設計が必要。担当者数によって並行化の設計が変わる |
| **品質基準** | 「どの状態になれば完成か」が不明な場合、タスクの完了基準が設定できない |

### ヒアリング不要なケース

以下の場合はフェーズ2をスキップして直接分解に進む:

- ゴール・成果物・期限・ツールが明示されており、標準的な進め方が1つに絞られる場合
- ユーザが詳細な条件を最初から提示している場合

この場合でも、置いた前提をWBS冒頭の「**前提・スコープ**」セクションに明記する。

---

## フェーズ2: コンテキストヒアリング

初期分析で不明点が残った場合、**`ask_user_input_v0` ツールを使用して**選択肢形式で質問する。文章での質問箇条書きは使わない。

### ヒアリング設計ルール

- **1回のツール呼び出しで最大3問**。優先度の高い順に絞る
- 各質問の選択肢は **2〜4個で相互排他的** にする
- 分解結果への影響が小さい項目は質問せず、標準的な前提を置いて進める
- ヒアリングは最大2往復。それ以上は推測した前提を明示して進める

### ヒアリング項目の典型例

1. **プロジェクトの期限**: 具体的な完了期限の有無と時期
2. **担当者の想定**: 個人作業か、複数人のチームか
3. **既存リソースの有無**: 流用できるテンプレート・ツール・ドキュメントがあるか
4. **承認・レビューフローの有無**: 上長確認・外部関係者の合意が必要か
5. **詳細度の要求レベル**: 大まかなロードマップで十分か、実行レベルの詳細が必要か

---

## フェーズ3: WBS設計

ヒアリング結果を踏まえ、WBSを設計する。

### フェーズ分割の指針

プロジェクト全体を **3〜7個のフェーズ** に分ける。フェーズは「この段階が完了すれば次の作業に進める」という意味のある区切りにする。

典型的なフェーズ構成の例:

| プロジェクト種別 | 典型的なフェーズ構成 |
|----------------|-------------------|
| ドキュメント整備 | 企画 → 構成設計 → 執筆 → レビュー → 公開 |
| 社内ツール導入 | 要件定義 → 選定 → 環境構築 → テスト → 展開 |
| イベント開催 | 企画 → 準備 → 告知 → 当日運営 → 振り返り |
| システム開発 | 要件定義 → 設計 → 実装 → テスト → リリース |

### タスクの粒度基準

各タスクは以下の**3基準すべてを満たす粒度**まで分解する:

| 基準 | 判定の問い |
|------|-----------|
| **完了判定可能性** | 「終わった」と客観的に判断できるか。「〜を検討する」は不合格。「〜の候補を3つリストアップし、比較表を作成する」は合格 |
| **単一作業性** | 実質的に1種類の作業か。複数の作業が混在していたら分割する |
| **工数見積可能性** | 半日〜2日の範囲で工数が見積もれるか。それを超える場合はさらに分割する |

### 工数の見積もり基準

| 工数 | 目安 |
|------|------|
| **0.5日** | 調査・確認・簡単な文書作成（2〜4時間） |
| **1日** | 標準的な資料作成・設定作業・レビュー（6〜8時間） |
| **2日** | 複雑な設計・実装・複数関係者との調整（12〜16時間） |

これを超える工数になる場合はタスクをさらに分割する。工数は楽観値ではなく、**初めて取り組む担当者を想定した現実的な値**を設定する。

### 依存関係の定義ルール

- 依存タスクは **タスクIDで参照** する（例: `T-01, T-02`）
- 依存関係がない（着手可能な）タスクは「なし」と記載する
- 並行して進められるタスクは依存先が共通の先行タスクのみを記載する

### タスクIDの付番ルール

- フェーズ番号とタスク連番を組み合わせた形式を使う: `T-[フェーズ番号]-[連番]`
  - 例: フェーズ1の1番目のタスク → `T-1-01`
- フェーズをまたいだ参照は完全なIDで記載する（例: `T-1-02`）

## フェーズ4: 表形式での出力

### 出力フォーマット

```
# [プロジェクト名] WBS

## 前提・スコープ
- **対象**: [誰が・何を・どの範囲で行うか]
- **完了定義**: [何の状態になればプロジェクトが完了か]
- **除外スコープ**: [明示的に対象外とする作業があれば記載]
- **前提条件**: [ヒアリングで確認した前提・置いた仮定]

## サマリー
- **フェーズ数**: X フェーズ
- **タスク総数**: XX タスク
- **総想定工数**: XX 日

---

## WBS

| タスクID | フェーズ | タスク名 | 成果物 | 想定工数 | 依存タスク |
|---------|---------|---------|--------|---------|----------|
| T-1-01 | 1. フェーズ名 | タスクの内容（動詞で終わる具体的な行動） | 成果物の名称 | 0.5日 | なし |
| T-1-02 | 1. フェーズ名 | ... | ... | 1日 | T-1-01 |
| ...    | ...     | ...  | ...   | ...  | ...     |

---

## 注意点・リスク

[分解の中で特に注意が必要なポイント、想定されるリスク、対処方針を2〜5点で記載]
```

### 出力時のルール

- タスク名は**動詞で終わる具体的な行動**として書く（「設計」ではなく「画面遷移図を作成する」）
- 成果物は**具体的な名詞**で書く（「ドキュメント」ではなく「要件定義書（Notion）」）
- 並行して進められるタスク群には、最初のタスクの直前にコメント行 `// 以下のタスクは並行実施可能` を入れる
- **タスク総数が40個を超える場合**は、直近の2フェーズのみ詳細に分解し、以降は粗い粒度に留めて「フェーズ◯着手時点で再分解推奨」と注記する
- 出力後に「**特定のフェーズの粒度調整や工数の見直しが必要な場合はお知らせください**」と一言添える

---

## 分解時の重要な姿勢

### 成果物から逆算する

タスクを前から積み上げるのではなく、**最終成果物から逆算**してどの作業が必要かを考える。「何をするか」ではなく「何が出来上がれば次に進めるか」を軸にする。

### 抜け漏れチェックの観点

分解後に以下を確認する:

- **承認・合意タスクの有無**: 関係者が複数いる場合、各フェーズ終了時のレビュー・承認タスクが含まれているか
- **環境準備タスクの有無**: ツール・アカウント・権限の準備が必要な場合、それが先行タスクとして入っているか
- **引き渡しタスクの有無**: 他者への共有・展開・トレーニングが必要な場合、最終フェーズに含まれているか
- **振り返りタスクの有無**: プロジェクト型の作業には完了後の評価・改善タスクを検討する

### 工数は保守的に見積もる

初学者・初回対応の担当者を想定した工数にする。「慣れた人なら半日」という楽観値は設定しない。調整が必要な場合はユーザに委ねる。

---

## 想定外の入力への対応

- **ゴールが複数混在している**: 「このスコープでよいか確認してから進めます」とスコープを提示し、合意を得てから1プロジェクト分を作成する
- **既存WBSの改善依頼**: ゼロから作り直さず、既存の構造をベースに「抜け漏れ・粒度・依存関係の問題」をレビューした上で改訂案を提示する
- **工数や期限が非現実的**: 分解結果の「注意点・リスク」セクションに明記し、スコープ削減またはリソース追加の検討を促す。非現実的な計画をそのまま出力しない
- **プロジェクトの種別が不明**: 最も一般的な「ドキュメント整備・社内展開」の構成を前提として提示し、冒頭に「以下の前提で作成しています」と明記する
