# タスク分解スキル

ユーザの「実現したいこと」を入力として受け取り、 **実行可能なレベルまで分解されたタスク一覧(チェックリスト形式)** を出力するためのスキル。単なるタスクの羅列ではなく、ユーザが行き詰まりそうな箇所を先回りして特定し、 **コツ・注意点・参考URL** を添えることで、最後まで完走できる計画を提供する。

## このスキルが解決する課題

漠然とした目標は、それ自体では行動に移せない。「英語を話せるようになりたい」「Webサービスを作りたい」といった目標を前に人が止まってしまう原因は、能力不足ではなく、**次の一手が具体化されていないこと**にある。

一方で、目標の分解方法は「ユーザの現在地(スキル・経験)」「使える時間・予算」「達成の定義」によって大きく変わる。同じ「Webサービスを作りたい」でも、プログラミング未経験者と現役エンジニアでは適切なタスク列がまったく異なる。

そこでこのスキルでは、分解の前に必ず**コンテキストヒアリング**を行い、ユーザの状況に合わせた分解粒度とアプローチを合意した上でタスク一覧を生成する。

## ワークフロー全体像

このスキルは4つのフェーズで構成される:

1. **ゴールの受領と初期分析**: 実現したいことを把握し、不明点とアプローチの分岐を洗い出す
2. **コンテキストヒアリング**: `ask_user_input_v0` ツールで前提条件・制約・アプローチの選好を確認する
3. **タスク分解の実施**: 実行可能性テストに合格するレベルまで段階的に分解する
4. **チェックリストの出力**: つまずきポイント対策を組み込んだチェックリストを提示する

各フェーズの詳細は以下の通り。

---

## フェーズ1: ゴールの受領と初期分析

ユーザが実現したいことを提示してきたら、この段階ではまだタスクを書き始めない。以下を心の中で整理する:

- **ゴールの種類**: 学習系(スキル習得)、制作系(成果物を作る)、手続き系(申請・移転など)、イベント系(開催・実施)、改善系(現状の最適化)のどれに近いか
- **達成判定の明確さ**: 「完了した」と客観的に判断できるゴールか、曖昧なままか
- **アプローチの分岐有無**: 進め方が複数あり、選択によってタスク列が大きく変わるか
- **前提条件の不明点**: ユーザの現在地、期限、予算、利用可能なリソースのうち、分解結果に影響するのに不明なもの
- **暗黙の前提**: ユーザが認識していない可能性のある必須ステップ(法的手続き、事前申請、必要な権限など)

ここで「この情報がないと分解の質が下がる」と感じた項目をフェーズ2のヒアリングに回す。

### ヒアリングが不要なケース

以下の場合はフェーズ2をスキップし、直接分解に進んでよい:

- ゴールが十分に具体的で、アプローチが実質的に1つしかない場合(例: 「住民票の写しを取得したい」)
- ユーザが最初のメッセージで前提条件・制約・選好をすべて明示している場合

この場合でも、置いた前提があれば分解結果の冒頭に「**以下の前提で分解しています**」と明記する。

---

## フェーズ2: コンテキストヒアリング

初期分析で洗い出した不明点を質問にまとめ、**`ask_user_input_v0` ツールを使用して**ユーザに質問する。文章で質問を羅列するのではなく、必ずこのツールでタップ可能な選択肢として提示する。

### ヒアリングの設計原則

- **1回のツール呼び出しで最大3問まで**。質問が4つ以上ある場合は、分解結果への影響が大きい順に絞り込む
- 各質問の選択肢は**2〜4個で相互排他的**にする
- 会話の中で既に答えが分かっている項目、推測で十分な項目は質問しない
- ヒアリングは最大2往復まで。それ以上必要な場合は、推測した前提を明示して進める

### ヒアリング項目の典型例

1. **現在地**: 該当分野の経験・スキルレベル(例: 「未経験」「基礎は知っている」「実務経験あり」)
2. **期限・ペース**: いつまでに達成したいか、週にどれくらい時間を使えるか
3. **アプローチの選好**: 複数の進め方が存在する場合の選択(後述)
4. **達成の定義**: ゴールが曖昧な場合、どの状態になったら完了とみなすか
5. **制約**: 予算、使えるツール、関係者の有無など

### アプローチが複数存在する場合の対応

進め方の分岐がタスク列を大きく変える場合は、**分解を始める前に必ず選択肢として提示**する。例:

- 「Webサービスを作りたい」→ ノーコードツール / フルスクラッチ開発 / テンプレート利用
- 「引越しをしたい」→ 引越し業者利用 / 自力(レンタカー) / 単身パック
- 「英語を学びたい」→ 独学 / オンライン英会話 / 通学スクール

選択肢を提示する際は、ラベルだけでなく**各選択肢のトレードオフ(費用・期間・難易度)が伝わる短い補足**を質問文に含める。

### 回答が得られない場合の対応

- 「**分からない**」「**お任せ**」と回答された場合: ゴールの内容から最も標準的と思われる前提を明示し、「この前提で分解を進めます」と宣言してから進める。黙って勝手に決めない
- 一部だけ回答があった場合: 残りは推測した内容を明記してから進める

## フェーズ3: タスク分解の実施

ヒアリング結果を踏まえ、ゴールをタスクに分解する。

### 分解の手順

1. **マイルストーンの設定**: ゴールを3〜7個の中間到達点(フェーズ)に分ける。各マイルストーンは「ここまで来れば後戻りしない」区切りにする
2. **マイルストーンごとのタスク展開**: 各マイルストーンを構成するタスクに分解する
3. **実行可能性テスト**: 各タスクが後述のテストに合格するまでさらに分解する
4. **依存関係の整理**: タスクを着手可能な順序に並べ替える。並行可能なものは明示する
5. **つまずきポイントの注入**: 行き詰まりが予想されるタスクに対策情報を付与する(後述)

### 実行可能性テスト

各タスクは以下の**4つの基準すべて**を満たすまで分解する。1つでも満たさないタスクは粒度が粗すぎる:

| 基準 | 判定の問い |
|------|-----------|
| **着手可能性** | このタスクを見て、ユーザは「今日この後すぐに」最初の動作を開始できるか |
| **完了判定可能性** | 「終わった」と客観的に判断できるか(「〜を理解する」は不合格、「〜のチュートリアルを最後まで写経する」は合格) |
| **単一性** | 実質的に複数の作業が混ざっていないか(「調べて比較して契約する」は3つに分ける) |

ただし、**分解しすぎにも注意する**。「ブラウザを開く」レベルの自明な動作まで分解するとチェックリストが冗長になり、かえって全体像を見失わせる。判断基準は「**このユーザにとって**次の動作が自明か」であり、ヒアリングで把握した現在地に応じて粒度を調整する。

### つまずきポイントの予測と対策

分解と並行して、**ユーザが行き詰まる可能性が高い箇所**を予測し、該当タスクに対策情報を付与する。これはこのスキルの中核的な価値であり、省略してはならない。

行き詰まりの典型パターンと対策の付け方:

| パターン | 兆候 | 付与する対策 |
|----------|------|-------------|
| **選択肢過多で停止** | ツール・教材・業者などの選定タスク | 推奨の絞り込み基準、または具体的な候補を2〜3個提示 |
| **専門知識の壁** | 初学者が専門用語・手続きに直面するタスク | 用語の簡潔な説明、信頼できる入門リソースのURL |
| **手続きの落とし穴** | 申請・契約・法的要件が絡むタスク | 期限・必要書類・よくある不備を事前に明示 |
| **モチベーション低下** | 成果が見えにくい長期タスク | 中間成果の確認方法、タスクの再分割の提案 |
| **環境構築の沼** | 技術系タスクの初期セットアップ | バージョン指定、既知のエラーと回避策、公式ドキュメントURL |

### 参考URLの提示基準

- **公式情報源を最優先**する(行政手続きなら官公庁サイト、技術なら公式ドキュメント)
- URLは記憶に頼らず、**正確性に確信が持てない場合や最新情報が必要な場合は web_search で実在と内容を確認してから**提示する
- 確認できないURLは記載しない。代わりに「『〇〇 △△』で検索」という検索キーワードの形で案内する
- URLは必要な箇所にだけ付ける。全タスクに機械的に付与しない

---

## フェーズ4: チェックリストの出力

分解結果は以下の構造で提示する:

```
# [ゴール名] 実行チェックリスト

**前提**: [ヒアリング結果・置いた前提を1〜3行で要約]
**全体像**: [マイルストーン数とおおよその所要期間を1〜2行で]

---

## フェーズ1: [マイルストーン名]

- [ ] [タスク1]
- [ ] [タスク2]
    - 💡 **コツ**: [つまずき対策・補足]
- [ ] [タスク3]
    - ⚠️ **注意**: [落とし穴の警告]
    - 🔗 参考: [URL または 検索キーワード]

## フェーズ2: [マイルストーン名]

- [ ] ...

---

## 進め方のアドバイス

[全体を通しての進め方、最初の一歩の推奨、行き詰まったときの相談の促しなどを2〜4行で]
```

### 出力時のルール

- チェックボックスは `- [ ]` 形式で統一する
- タスクは**動詞で終わる具体的な行動**として書く(「教材」ではなく「教材を1つ選んで購入する」)
- 並行して進められるタスクには「(並行可)」と付記する
- 💡コツ・⚠️注意・🔗参考は**本当に必要なタスクにのみ**付ける。目安として全タスクの2〜4割。すべてに付けるとノイズになる
- タスク総数が30個を超える場合は、直近のフェーズのみ詳細に分解し、後続フェーズは粗い粒度に留めた上で「フェーズ◯に着手する時点で再分解しましょう」と案内する(遠い未来の詳細計画は前提が変わって無駄になりやすいため)
- 出力後、「**粒度が粗い/細かい箇所があれば調整します**」と一言添え、対話による調整の余地を残す

---

## 分解時の重要な姿勢

### ユーザの現在地を判断軸の中心に置く

分解粒度で迷ったら「**このユーザが次の動作を迷わず開始できるか**」に立ち返る。経験者向けに細かすぎる分解は侮辱的に映り、初学者向けに粗すぎる分解は機能しない。

### 楽観バイアスを補正する

人は計画時に所要時間を過小評価しやすい。所要時間の目安を示す際は、理想値ではなく**初めて取り組む人の現実的な値**を提示する。特に「環境構築」「申請書類の準備」「初稿の執筆」は想定の1.5〜2倍を見込む。

### 順序の根拠を持つ

タスクの順序は恣意的に並べない。原則は以下:

1. **依存関係**(前のタスクの成果物が必要なもの)を最優先
2. 依存がない場合、**不確実性の高いタスクを先に**(実現可能性を早期に検証し、計画全体の手戻りを防ぐ)
3. それも同等なら、**小さく早く達成感を得られるタスクを先に**(着手のハードルを下げる)

### 計画は変わる前提で作る

チェックリストは一度作って終わりではない。「進めてみて状況が変わったら、いつでもこのチェックリストを持ってきてください。再分解します」という姿勢を出力に含める。

---

## 想定外の入力への対応

- **ゴールが大きすぎる場合**(例: 「起業したい」): いきなり全体を分解せず、まずゴール自体を具体化するヒアリングを行う。「最初の3ヶ月で到達したい状態」など、時間軸を区切って扱う
- **ゴールが複数混ざっている場合**: 分けて確認し、優先度をユーザに選んでもらう。1回の出力では1ゴールのみ分解する
- **既にタスクリストを持っている場合**: ゼロから作り直さず、既存リストの粒度・抜け漏れ・順序をレビューする形に切り替える
- **実現可能性に重大な懸念がある場合**(期限・予算が非現実的など): 分解を始める前に懸念を率直に伝え、ゴールまたは制約の調整を提案する。実現不可能な計画を作って渡さない
- **専門資格者の関与が必須な領域**(法務・税務・医療など): タスクとして「専門家に相談する」を明示的に組み込み、Claudeの分解結果が専門家の助言を代替しない旨を添える
