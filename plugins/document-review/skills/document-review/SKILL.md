# ドキュメントレビュースキル

任意形式のドキュメントを入力として受け取り、**幅広い観点でレビューしたうえで、優先度順の推奨事項をまとめた Markdown レポートを出力する**スキル。

このスキルの成果物は、**著者がレポートを上から順に対応していけば、文書の品質が確実に上がる**ことを最優先の品質基準とする。

## このスキルが解決する課題

レビューの失敗には2つの典型がある。ひとつは **表層に張りつく失敗** で、誤字脱字は丁寧に拾えているのに「そもそもこの資料は読み手の意思決定に必要な情報を載せていない」という致命的な問題を見逃す。もうひとつは **抽象論で終わる失敗** で、「構成を整理するとよい」といった感想は述べるが、著者がどこをどう直せばよいか分からない。

さらに、指摘が大量に並んでいても優先度がなければ、著者は結局どこから手をつけるか分からず、レビューは活用されない。

そこでこのスキルでは、**抽象から具象へ向かう5つの観点レイヤーで漏れなく読み**、**すべての指摘を「箇所・現状・問題・推奨」の4点セットに揃え**、**影響度と確実性で優先度を付けて並べ替える**。時間をかけて何度も読み返すことを前提とし、1回通読しただけで書き始めることはしない。

## ワークフロー全体像

1. **取り込みと文脈把握**: 文書を読み取り、目的・想定読者・種別を特定する
2. **多層レビュー**: 4つのパスで繰り返し読み、観点レイヤーごとに所見を蓄積する
3. **指摘の検証と優先度付け**: 憶測を排し、影響度×確実性で並べ替える
4. **レポート作成**: Markdown ファイルとして出力し、ユーザに提示する
5. **フィードバック対応**: 指摘の妥当性を議論し、必要なら更新する

## フェーズ1: 取り込みと文脈把握

### 1-1. 文書を読み取る

`scripts/extract_document.py` を使い、位置情報つきテキストに変換する。位置情報（ページ番号・スライド番号・段落番号・セル番地・行番号）は、後で「どこの指摘か」を著者に伝えるために不可欠なので、素の本文だけを取り出す方法は使わない。

```bash
python3 <skill-path>/scripts/extract_document.py <file> [<file> ...] -o /tmp/extracted.txt
```

対応形式は docx / dotx / pptx / potx / xlsx / xlsm / csv / tsv / pdf / md / txt / html と、LibreOffice 経由の doc / ppt / xls / odt / odp / ods。

読み取りで詰まったときの補助:

- **スキャン画像 PDF**（抽出テキストがほぼ空）: ページを画像化して目視で読む。`/mnt/skills/public/pdf-reading/SKILL.md` があればそれに従う
- **図・スクリーンショットが情報の中心を担っている場合**: テキスト抽出だけでは判断できない。画像として確認するか、それが無理ならレポートに「図の内容は未検証」と明記する
- **変更履歴やコメントが付いた Word 文書**: `/mnt/skills/public/docx/SKILL.md` を参照する。未解決のコメントや残った変更履歴は、それ自体が指摘対象になる
- **テキストが文脈として既に読み込まれている場合**: 抽出をやり直す必要はないが、位置情報が失われているなら見出し名やページ番号を自分で補って参照できるようにする

### 1-2. 文書の全量を把握する

抽出結果の分量（文字数・ページ数・スライド数・シート数）を確認し、**全体を読み切る前提で計画を立てる**。長いという理由で冒頭と結論だけを読み、中間を飛ばしてはならない。飛ばした部分にこそ、著者が疲れて雑になった箇所や整合性の崩れが潜んでいる。

### 1-3. 文脈を特定する

以下の4点を、文書自体から読み取る。レビューの妥当性はここで決まる。同じ文章でも、社内向けの叩き台と顧客提出版では「良い」の基準がまったく違う。

| 項目 | 何を特定するか |
|------|----------------|
| **目的** | この文書は読者に何をさせたいのか（承認を得る／理解させる／作業させる／記録を残す） |
| **想定読者** | 誰が読むのか。前提知識の水準、意思決定権の有無、社内か社外か |
| **文書種別** | 提案書・報告書・議事録・設計書・仕様書・手順書・記事・マニュアルなど |
| **完成度** | 初稿の叩き台か、提出直前の最終版か。求める精度が変わる |

### 1-4. 読み取れないときだけ確認する

上記4点のうち**文書から読み取れず、かつレビュー結果を左右する項目がある場合に限り**、`ask_user_input_v0` ツールで確認する。読み取れるものをわざわざ聞くとユーザの時間を奪うだけなので、質問は本当に必要なものに絞る。

質問の設計は、1回の呼び出しで最大3問、各質問の選択肢は2〜4個で相互排他的にする。ツールが使えない環境では文章で簡潔に尋ねる。

判断に迷う典型例:

- 文書に目的が明記されておらず、内容からも複数の解釈が成り立つ → **確認する**
- 想定読者が社内か社外かで、用語の説明要否や機密情報の扱いが変わる → **確認する**
- 表紙に「提案書」とあり構成も提案書の形をしている → **確認しない**（読み取れている）
- 重点的に見てほしい観点があるかどうか → 幅広くレビューするのが本スキルの前提なので、**原則確認しない**。ただしユーザが最初から特定の観点（例:「セキュリティ面だけ見て」）を指定してきた場合は、その観点を厚くしつつ他の層も最低限は見る

読み取れない項目があっても確認せずに進める場合は、**置いた前提をレポートの冒頭に明記する**。前提が違えば指摘も変わるため、著者が判断できるようにしておく。

## フェーズ2: 多層レビュー

### 観点の5レイヤー

観点は抽象度で5層に分かれる。詳細なチェックリストは **`references/review-perspectives.md`** にあるので、レビュー開始時に必ず読むこと。

| レイヤー | 観点 | 問い |
|---------|------|------|
| **L1 目的適合性** | 目的・読者・スコープ | この文書は目的を果たすか。読者にとって過不足ないか |
| **L2 全体構成** | 論理構造・情報配置 | 章立ては筋が通っているか。順序・粒度・重複・欠落はどうか |
| **L3 内容の妥当性** | 主張と根拠・整合性 | 主張は根拠に支えられているか。数値・事実・記述は矛盾しないか |
| **L4 記述・表現** | 明確さ・一貫性 | 一読して意味が取れるか。用語・文体は統一されているか |
| **L5 表記・体裁** | 誤字脱字・書式 | 誤字脱字、表記ゆれ、書式の乱れ、図表番号やリンクの不備はないか |

文書種別ごとの追加観点（提案書なら費用対効果の提示、議事録なら決定事項と担当者の明記など）は **`references/document-types.md`** にまとめてある。フェーズ1で特定した種別の節を読むこと。

### 4パスで読む

**1回読んだだけでレポートを書き始めてはならない。** 人が文書を読むとき、全体像を掴む読み方と誤字を拾う読み方は両立しない。だから読み方を変えて複数回通す。所要時間を惜しまないこと。

**パス1 — 通読（L1）**
指摘を取らずに最後まで読む。読み終えて「この文書は結局何を言っていて、読者に何をさせたいのか」を1〜2文で言えるようにする。言えないなら、それ自体が L1 の重大な指摘である。

**パス2 — 構造の検分（L2・L3）**
目次・見出し・図表だけを抜き出して骨格を並べ、章の順序と粒度、抜けと重複を検分する。次に各章の主張と根拠の対応を確認し、数値・日付・固有名詞が文書内で一貫しているかを突き合わせる。数値の突き合わせは記憶に頼らず、抽出テキストから該当箇所を grep して確認する。

**パス3 — 精読（L4・L5）**
先頭から1文ずつ読み、表現の曖昧さ・冗長さ・誤字脱字・表記ゆれを拾う。この段階では細部に集中し、構成の是非は考えない。**全ページ・全スライド・全シートを対象にする。**

**パス4 — 読者としての通し読み（L1 再確認）**
想定読者になりきってもう一度通す。前提知識のない読者が詰まる箇所、意思決定に必要なのに書かれていない情報、誤読しうる表現を探す。ここで見つかる指摘は往々にして最も価値が高い。

### 所見のメモの取り方

各パスで見つけたことは、その場で以下の形にして書き留める。後でまとめて書こうとすると、位置情報と問題意識が失われる。

```
[箇所] p.3 / 第2章 / ¶14 / スライド5 / 集計!B4 など
[現状] 実際にどう書かれているか（短く引用または要約）
[問題] 何が問題で、放置するとどうなるか
[推奨] どう直せばよいか（可能なら修正後の文案そのもの）
[レイヤー] L1〜L5
```

**推奨は具体的に書く。** 「表現を見直す」ではなく「『対応を検討する』→『4月末までに A 部が対応方針を決定する』のように主体と期限を明示する」と書く。著者がそのまま使える文案まで踏み込めるなら、そこまで書く。

### 憶測で断定しない

事実関係を文書内で検証できない指摘（外部の数値の正しさ、業界慣行との整合、社内規程との適合など）は、**「誤り」と断定せず「要確認」として扱う**。断定は著者の信頼を損ない、かえってレポート全体が軽んじられる。

- 文書内で矛盾している → **指摘**（例: 3ページの合計と5ページの表の合計が一致しない）
- 文書外の事実に依存する → **要確認**（例: この単価は最新の見積と一致しているか確認が必要）
- Web 検索で確かめられ、かつ確認する価値が高い → **検索して裏を取る**（ツールが使える場合）

### 網羅性のセルフチェック

レポート作成に進む前に確認する。ひとつでも「いいえ」があるなら、そのパスに戻る。

- 全ページ・全スライド・全シートに目を通したか
- L1 から L5 まで、どのレイヤーにも少なくとも一度は意識を向けたか
- 文書種別ごとの追加観点を確認したか
- 良い点も拾ったか（後述）
- 「読者が知りたいのに書かれていないこと」を探したか（書かれていることだけを見ていないか）

## フェーズ3: 指摘の検証と優先度付け

### 優先度の判定

**影響度**（放置したときに何が起きるか）と **確実性**（本当に問題だと言い切れるか）の2軸で決める。影響度を優先し、確実性は同程度の影響度のなかでの順位付けに使う。

| 優先度 | 基準 | 例 |
|-------|------|-----|
| **P0 致命的** | 目的が達成できない、読者を誤らせる、事実誤認・法令や機密上の問題を含む | 結論が根拠と矛盾している／必須の承認事項が書かれていない／社外秘情報が社外向け資料に載っている |
| **P1 重要** | 目的は果たすが、読者が誤読・困惑する。説得力や実務上の使い勝手を大きく損なう | 主張に根拠がない／手順書に前提条件が抜けている／章の順序が読者の思考順と逆 |
| **P2 改善推奨** | 品質が目に見えて上がるが、なくても文書は機能する | 冗長な表現／図表があると分かりやすい箇所／用語の不統一 |
| **P3 任意** | 好みや軽微な体裁。対応は著者の裁量 | 語尾のリズム／体裁の微調整 |

判断に迷ったら「**この指摘を無視して文書が世に出たとき、誰がどう困るか**」を考える。困る人が具体的に浮かべば P1 以上、浮かばなければ P2 以下。

**誤字脱字は原則 P2** としてまとめて扱う。ただし、社名・人名・金額・日付の誤りや、意味が反転する誤変換は読者を実害に導くので **P0 または P1** に引き上げる。

### 指摘の統合と整理

同じ原因から生じている複数の指摘は、**1件にまとめて「他にも X 箇所で同様」と添える**。同じ指摘が20件並ぶと、レポートが読まれなくなる。一方で、誤字脱字のような機械的な指摘は、著者が一括で直せるよう**一覧表として全件列挙する**。

### 良い点も必ず拾う

レビューは欠点の列挙ではない。優れている箇所を具体的に指摘することには実用的な意味がある。著者が改稿の過程でその強みを壊すのを防げるし、他の章に横展開できる型を教えることにもなる。「全体的に丁寧です」のような社交辞令ではなく、**どこがなぜ良いか**を書く。

## フェーズ4: レポート作成

レビュー結果は **Markdown ファイル** として出力する。

### 出力先

- `/mnt/user-data/outputs/` が存在すればそこに書き、`present_files` ツールで提示する
- 存在しない環境では、入力ファイルと同じディレクトリか作業ディレクトリに書き、パスを伝える
- ファイル名は `review_<元文書名>_<YYYYMMDD>.md`

### 構成

**`references/report-template.md` を読み、その構成に従って書くこと。** テンプレートには各セクションの書き方と記入例が含まれている。

概略は以下の通り。

```markdown
# レビューレポート: <文書名>
## 1. レビュー概要      … 対象・前提・指摘件数サマリ
## 2. 総評              … 全体所感と良い点
## 3. 推奨事項（優先度順）… レポートの中核。P0 から順に並べる
## 4. 観点別レビュー結果  … L1〜L5 それぞれの所見
## 5. 表記・誤字脱字の指摘一覧 … 一括修正用の表
## 6. 要確認事項          … 文書内では判断できなかった事項
```

### 書くときの原則

- **推奨事項は優先度順に並べる**。レイヤー順や登場順ではない。著者は上から順に対応すればよい状態にする
- 各指摘に **一意の ID**（`P0-1`, `P1-3` など）を付ける。ユーザとの議論で参照できるようにするため
- **該当箇所は必ず位置情報つきで示す**。「本文中の記載」ではなく「p.4 第3章 2段落目」と書く
- 引用は指摘の特定に必要な最小限にとどめる。文書を丸ごと再掲しない
- 文書の書き手を評価する言葉（「雑」「理解不足」など）は使わない。**文書に対して**書く
- 指摘がゼロのレイヤーがあれば、無理に絞り出さず「特筆すべき問題なし」と書く

## フェーズ5: フィードバック対応

レポート提示後、ユーザから反論や質問があった場合、**指摘を撤回する前にまず妥当性を再検討する**。

1. **こちらの誤読だった場合**: 率直に認め、レポートを更新する
2. **文書外の文脈（社内の暗黙の合意、既に共有済みの情報など）により指摘が不要な場合**: 納得して取り下げるが、「その文脈を知らない読者には同じ疑問が生じうる」点は伝える価値があるか検討する
3. **指摘が依然として妥当だと考える場合**: 安易に引っ込めず、なぜそう考えるかを根拠とともに説明する。ただし押し付けず、最終判断は著者に委ねる

修正版の文書が再提出された場合は、**前回の指摘が解消されたかを確認したうえで、新たに生じた問題も見る**。修正は往々にして別の不整合を生む。

## 想定外の入力への対応

- **複数ファイルが一括で渡された場合**: それぞれを個別にレビューしたうえで、**ファイル間の整合性**（数値の食い違い、用語の不統一、重複や矛盾）も観点に加える。レポートは1本にまとめ、ファイルごとに節を分ける
- **文書が極端に短い場合**（1枚もの、数百字）: パス構成は維持しつつ簡略化してよいが、L1 の目的適合性は必ず見る。短い文書ほど目的とのズレが致命傷になる
- **文書が極端に長い場合**（数百ページ）: 全体を読む方針は変えない。ただしパス3の精読は、まず全体をざっと通して問題が集中している章を特定し、そこを重点的に精読したうえで、他章は代表的な指摘を拾う形にしてよい。この場合は**どこを重点的に見たかをレポートに明記する**
- **未完成・執筆途中の文書**: 未執筆箇所を「指摘」として列挙しても価値がない。完成済み部分の品質と、全体構成の妥当性に絞ってレビューし、その方針を冒頭に書く
- **専門領域が絡む場合**（法務・医療・会計・セキュリティなど）: 一般的な文書品質の観点でレビューしつつ、専門的判断が必要な箇所は「要確認事項」に分類し、専門家の確認を推奨する。専門家のふりをして断定しない
- **コードやデータそのものが中心の場合**: 本スキルの対象は文書品質。コードレビューやデータ分析が本題なら、そちらを主眼に切り替えるかユーザに確認する
- **レビューではなく修正まで求められた場合**: レポートを作ったうえで、「修正版の作成も可能」と提案する。元ファイルを勝手に上書きしない
