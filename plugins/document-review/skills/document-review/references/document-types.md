# 文書種別ごとの追加観点

L1〜L5 の共通観点（`review-perspectives.md`）に加えて見るべき、種別固有の点。

**使い方**: フェーズ1で特定した種別の節を読む。種別が判別できないときや複数の性格を併せ持つときは、近いものを複数読んでよい。ここにない種別の場合は、**「この種類の文書が読者にとって役に立つ状態とは何か」を自分で定義してから**レビューに入ること。

## 提案書・企画書

読者は**投資判断をする人**。「やるべきか」を判断できるかがすべて。

- 解決したい課題が、提案の前に具体的に示されているか。課題が曖昧なまま解決策が語られていないか
- 提案内容が、課題に対する解になっているか。手段が目的化していないか
- **費用**が示されているか。初期費用だけでなく運用費・人件費・隠れコストを含むか
- **効果**が示され、可能なら定量化されているか。効果の測り方が定義されているか
- **リスクと前提**が正直に書かれているか。うまくいかない場合の想定があるか
- **代替案**が検討され、なぜこの案かが説明されているか。「何もしない」案との比較があるか
- スケジュールと体制が、実行可能な粒度で示されているか
- 意思決定者に**何を承認してほしいのか**が明示されているか
- 競合・他社事例に言及する場合、出典と公平性があるか

## 報告書・調査レポート

読者は**事実を知り、次の判断に使う人**。事実と解釈の分離が生命線。

- 結論・要点が冒頭にあるか。読者が全文を読まないと要点を掴めない構成になっていないか
- **事実・データ**と**著者の解釈・意見**が読み分けられるか
- 調査の方法・範囲・期間・サンプル数が明示されているか。一般化の限界に触れているか
- データの出典と取得時点が示されているか
- 想定と異なる結果・失敗・限界も報告されているか（都合のよい部分だけになっていないか）
- 結論が示唆する**次のアクション**が書かれているか
- グラフ・表が結論を支えているか。印象操作になっていないか

## 議事録・会議メモ

読者は**欠席者と、後から経緯を確認する人**。情報の欠落が最大の敵。

- 日時・場所・出席者（欠席者）・議題が記録されているか
- **決定事項**が、決定だと分かる形で独立して書かれているか
- **未決事項**が、いつ誰がどう決めるかとともに書かれているか
- **ToDo** に担当者と期限が付いているか。「〜する方向で」で終わっていないか
- 決定に至った**理由・検討の経緯**が残っているか（結論だけだと後で蒸し返される）
- 反対意見・懸念が記録されているか
- 発言の帰属が正確か。特定個人に不利益となる記述が不用意に残っていないか
- 前回議事録からの継続事項が追えるか

## 設計書・仕様書

読者は**これを読んで実装・検証する人**。曖昧さがそのまま手戻りになる。

- 実装者が読んで、**追加の質問なしに実装に着手できる**粒度か
- 前提・制約・スコープ外が明示されているか
- インタフェース（入力・出力・形式・型・必須任意・上限）が定義されているか
- **異常系・エラー処理・境界値**が書かれているか。正常系だけになっていないか
- 非機能要件（性能・可用性・セキュリティ・保守性）が測定可能な形で書かれているか
- 図（構成図・シーケンス・状態遷移・ER）と本文が一致しているか
- 設計判断の**理由**が残っているか。後任が「なぜこうなっているか」を追えるか
- 用語がプロジェクト内で定義され、一貫して使われているか
- 既存システムとの関係、移行・互換性が扱われているか
- テスト・検証の観点が書かれている、または別文書への参照があるか

## 手順書・運用マニュアル

読者は**緊張状態でこれを見ながら作業する人**。読者は急いでいて、読み飛ばす。

- 手順に**番号が振られ、順序が明確**か
- 各手順の**完了判定**（何が表示されたら成功か）が書かれているか
- 開始前の**前提条件**（権限、環境、必要なもの）が冒頭にまとまっているか
- 1手順に複数の操作が詰め込まれていないか
- 操作対象が一意に特定できるか（画面名・ボタン名・パスが実物と一致するか）
- **失敗時・異常時の対応**が書かれているか。どこまで戻ればよいかが分かるか
- 危険な操作（削除、本番反映、不可逆な変更）に警告があるか
- 判断が必要な分岐が、条件とともに明示されているか
- 更新日と適用範囲（対象バージョン・環境）が書かれているか

## ユーザ向けマニュアル・ヘルプ

読者は**製品に詳しくない人**。提供者の都合で書かれていないかを疑う。

- 機能の説明ではなく、**ユーザがやりたいこと**から入っているか
- 社内用語・開発用語がそのまま出ていないか
- 初めての読者がつまずく箇所に、説明や図が置かれているか
- 用語の初出時に説明があるか
- 目的から目的の項目に辿り着けるか（目次・索引・見出しの言葉選び）
- スクリーンショットが現行 UI と一致しているか
- よくある失敗とその対処が扱われているか

## 記事・ブログ・広報文

読者は**いつでも離脱できる人**。最初の数行で読み続ける理由を与えられるか。

- 冒頭で読者に「自分に関係がある」と伝わるか
- タイトルと中身が一致しているか。誇張や釣りになっていないか
- 1つの記事が1つのテーマに絞られているか
- 主張に根拠・具体例があるか。抽象論だけで終わっていないか
- 読者の知識水準に対して、説明の厚みが適切か
- 文章のリズム、段落の切り方、見出しの入れ方が読みやすいか
- 引用・画像の出典と権利処理が適切か
- 事実の誤り、誤解を招く表現、炎上しうる表現がないか
- 対外文書として、社名・製品名の表記が正式名称と一致しているか
- 結びで読者に何をしてほしいかが示されているか

## プレゼン資料

読者は**話を聞きながら、または後から資料だけを見る人**。両方の使われ方を想定する。

- **1スライド1メッセージ**になっているか。複数の論点が同居していないか
- スライドのタイトルが、そのスライドの**結論**を表しているか（「売上推移」より「売上は3期連続で伸長」）
- 情報量が過多でないか。文字が小さくなりすぎていないか
- **資料単体で読んだときに意味が通るか**（口頭説明前提の穴がないか）
- ストーリーの流れがスライド順で追えるか
- グラフ・図の軸・単位・凡例・出典があるか
- 表紙・アジェンダ・まとめ・次アクションのスライドが必要に応じてあるか
- テンプレート・配色・フォントが統一されているか
- 発表者ノートに社内向けの生々しい記述が残っていないか
- 想定質疑への備え（Appendix）があるか

## 表計算・データシート

読者は**数字を信じて意思決定する人**。計算の正しさと再現性が問われる。

- **数式エラー**（#REF! #VALUE! #DIV/0! #N/A）が残っていないか
- 数式の**参照範囲**が正しいか。行追加で範囲がずれていないか
- 数式に**ハードコードされた値**が埋め込まれていないか（後から変更できない）
- 入力セルと計算セルが区別されているか
- 単位・通貨・税込税抜・期間の定義が明示されているか
- 集計値と内訳の合計が一致するか
- **前提条件・パラメータ**がシート上に明示され、変更できるようになっているか
- 非表示のシート・行・列に、見せるべきでない情報や古い情報が残っていないか
- 他人が開いて理解できるか（シート名、列見出し、注記）
- フィルタ・並べ替えが掛かったまま保存されていないか
- 端数処理・丸めの方針が一貫しているか

## 規程・ポリシー・契約関連

読者は**これに従う人と、これを根拠に判断する人**。解釈の余地が事故になる。

- 適用範囲（対象者・対象業務・期間）が明確か
- 「〜すること」「〜してはならない」「〜が望ましい」の強制力の違いが区別されているか
- 曖昧語（「適切に」「原則として」「必要に応じて」）が、判断が必要な箇所で使われていないか
- 例外規定と、例外を認める主体・手続きが定義されているか
- 用語が定義され、定義どおりに使われているか
- 他の規程・法令との関係、上位下位が示されているか
- 違反時の扱い、責任の所在が書かれているか
- 改定日・施行日・改定履歴があるか

**重要**: 法的な有効性・適法性の判断は行わない。気になる点は「要確認事項」として挙げ、法務・専門家の確認を推奨する。
